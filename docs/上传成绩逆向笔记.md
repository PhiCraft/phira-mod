# 成绩上传：逆向笔记（目标：让开源构建也能上传）

> 结论先行：**上传在开源构建里是死代码**，但**逆向出来是可行的**，因为官方客户端没被 strip，
> 编码器是可定位、可分析的真实函数。这份笔记记录已确认的事实、还缺什么、下一步怎么做。

## 1. 为什么开源构建传不了（已确认）

| 事实 | 出处 |
|---|---|
| `rated` 硬编码为 false | `phira/src/scene/song.rs`：`#[cfg(not(closed))] let rated = false;` |
| 于是每局都弹 `warn-unrated`（"本局成绩不计入排行"） | 同文件，`if !rated && can_rated && mode == GameMode::Normal` |
| 上传数据在引擎里构造 | `prpr/src/scene/game.rs` 的 `#[cfg(closed)]` 块：`record_data = Some(encode_record(self, player.id, *chart))` |
| `encode_record` 在仓库里**没有定义** | 全仓库搜索只找到那一处调用 |
| 闭源模块 | `prpr/src/scene/game.rs:114`：`#[cfg(closed)] mod inner;`（`inner.rs` 不在仓库里）|

上传接口本身是**开放可见**的（在 `phira/src/scene/song.rs` 里）：

```rust
Client::post("/play/upload", &Req {
    chart: i32,
    token: String,                      // = STANDARD.encode(record_data)
    chart_updated: Option<DateTime<Utc>>,
})
```

也就是说：**接口不需要逆向，缺的是 `record_data`（token）那个 blob 怎么生成**。

## 7. 第一轮反汇编结果（重要）

### 7.1 `resolve_data`（156 B）—— 结构已看清

```
sub sp …（栈帧）
bl  custom_dec@plt          ← 解密，参数是 (x0 = 输入指针, x8 = 输出槽)
ldr q0, [x20] / stp …       ← 把结果按 Rust 的 String/Vec 布局（ptr,len,cap 3 个字）搬走
bl  0x9643a4                ← 再走一步（压缩/解析之类）
失败路径：构造一个 40 字节的错误消息 + panic
```
⇒ 它就是「custom_dec + 后处理」的薄包装。**调用约定**：`custom_dec(x0=输入, x8=返回槽)`。

### 7.2 `custom_enc`（1884 B）—— **被混淆了**

开头就是典型的不透明常量 + 间接调用：

```asm
mov/movk ×4   → x24 = 0xddec255692d89ce9     ← 64 位不透明常量
adrp x8, 0x18c3000 ; ldr x8, [x8, #0x2a8]    ← 取全局指针
ldr  x8, [x8, x24]                           ← 用巨大偏移取数据
mov/movk ×4   → x10 = 0x779fe40f101c93b0
add  x8, x8, x10
blr  x8                                      ← 间接调用（真实目标运行时才算得出）
```
⇒ 直接读死代码没用，要动态跟或者把常量表解出来。**这是本次逆向最硬的一块。**

### 7.3 `encode_record`（6328 B / 1588 行）—— **没有混淆** ✅

统计：`blr` = 0、`br` = 0、`movk` = 0 —— 全是直接调用和普通常量。
反复引用 `0x18c3000` 段（全局表/重定位区）和 `0x275000` 段（常量与字符串）。

⇒ **记录的序列化部分是能读懂的**：它大概做三件事
1. 把成绩字段（chart id / player id / 分数 / 准度 / 判定计数 / 版本等）拼成一段内存
2. 调用 `custom_enc` 加密（唯一难读的部分）
3. 可能再叠一层压缩（官方 .so 里带 zstd）

### 7.4 结论：难度重新评估

| 部分 | 难度 | 说明 |
|---|---|---|
| 上传接口调用 | 无 | 开源树里就有（`/play/upload` + base64 token）|
| 记录序列化 | **中** | `encode_record` 未混淆，可读；1588 行要耐心读 |
| 加密（`custom_enc`/`custom_dec`） | **高** | 被混淆，需动态调试或解常量表 |
| 服务端额外校验 | **未知** | 只有真机实测才知道 |

**两条路，成本差很多：**

- **A. 抓包（快）**：在真机上用 mitmproxy 抓一次官方客户端的真实上传请求，
  拿到 token blob → 看它是不是 `zstd + 明文 protobuf`。
  如果是明文（只是 base64/压缩），**当天就能实现**，根本不用啃 `custom_enc`。
  需要你：手机、已登录账号、装信任证书、打一局官方谱面。
- **B. 纯静态逆向（慢、不确定）**：把 `custom_enc` 的混淆解开 + 读 1588 行
  `encode_record`。要几轮，且**如果密钥是运行时派生/从服务器拿的，静态根本拿不到**。

建议先做 A（成本低、结论明确）；A 抓到的 blob 也正好能验证 B 的成果。

### 8.3 分析结论

| 指标 | 值 | 含义 |

| 长度 | 133 字节 | 固定长度 ⇒ 定长结构，不是变长 protobuf |

### 8.4 下一步需要的数据（决定性）

**同一张谱面（46304）再上传 2–3 次，分数各不相同。** 理由：
1. 逐字节对比 → 直接看出**哪些字节编码分数/准度/判定数**（变的就是它们）
2. 两条等长数据**异或** → 若出现长串相同的值，就证明是"明文 ⊕ 固定 keystream"，
   可进一步推出 keystream；若异或结果仍高熵，则 keystream 与位置/时间相关
3. 再抓一条**不同谱面** → 定位 chart id 字段
4. 若能重打出一模一样的分数 → 可判断有没有 nonce/时间戳（相同输入是否产生相同输出）

⚠️ 新风险：若尾部确实是服务端校验用的 MAC/签名，那么**光会编码还不够**，
还要能算出 MAC —— 那需要密钥，静态逆向 `custom_enc` 就绕不过去了。
下一批样本能直接验证这一点（若两次上传的尾段呈现"整体高熵但长度固定"，
且头段呈现明显差分，就基本能确认是「混淆字段 + 独立 MAC」的结构）。

## 9. 静态逆向 `custom_enc`：混淆方案已解开

### 9.1 混淆手法（已破解并验证两次）

它的「不透明常量 + 巨型偏移」其实是**指针隐藏**，规则是：

```
真实地址 = 重定位表里的值 + 不透明常量   (按 2^64 回绕)
```

**验证 1**（GOT 取数）：
```
槽 0x18c32a8 的 R_AARCH64_RELATIVE addend = 0x2213daa96eb39567
混淆常量 x24                              = 0xddec255692d89ce9
相加（mod 2^64）                           = 0x00000000018c3250   ✓ 合法地址
```
**验证 2**（间接调用目标，槽的值是负数）：
```
槽 0x18c3250 的 addend = -0x779fe40f0f49d128 ≡ 0x88601bf0f0b62ed8
加上混淆增量 x10        = 0x779fe40f101c93b0
相加（回绕）            = 0x0000000000D2C288   ✓ 真实目标
```

⇒ 只要能从 `-R` 拿到槽的 addend，**任何一处隐藏调用/数据都能算出来**。
工具：`llvm-objdump -d`（反汇编）+ `llvm-objdump -R`（重定位），都在 NDK 里。

### 9.2 已解出的那个间接调用 = `Vec::resize`

`custom_enc` 全函数只有 **1 处 `blr`、0 处 `bl`**（477 行反汇编）。那个 blr 的目标 `0xD2C288`
反汇编出来是标准库辅助：

```
ldr x19, [x0, #0x10]     ; Vec 的 len
subs x20, x1, x19        ; 目标长度 - 当前长度
bl  memset@plt           ; 扩容后补零
strb w2, [x8]            ; 写入字节
str x1, [x0, #0x10]      ; 回写 len
```
⇒ 就是 `Vec::resize(len, byte)` 一类。**不是加密核心** —— 也就是说
**加密逻辑是内联在 `custom_enc` 的 477 行里的**，没有单独的核心函数可找。

### 9.3 观察：常量成族

x19/x21/x22/x23/x25/x26/x27/x28 的高 32 位全是 `0xffea5921`，
只有低 32 位不同 ⇒ 它们是**同一基准下的 8 个隐藏指针**（delta 形式）。
用 9.1 的方法逐个还原，就能把 477 行里 23 处寄存器偏移取数全部映射成
「哪次是 memcpy / memset / Vec 操作 / 真正的逻辑」，剩下的才是要读的算法本体。

### 9.4 下一步（按顺序）

1. 脚本化：把 `custom_enc` 里 23 处 `ldr xN,[xN,xN]` 的 (槽, 常量) 全部解出真实地址，
   逐个反汇编，标注成辅助函数还是逻辑 —— 把 477 行里"噪音"删掉
2. 精读剩下的真逻辑：目标是还原那个**非线性变换**（8.3 节证明它不是单纯异或）
3. 同时读 `encode_record`（1588 行、未混淆）确定**明文字段布局**
   （已知：chart=46304、chartUpdated、分数 9550/109839 —— 但分数在任何简单编码里都找不到，
   说明序列化本身也带变换）
4. 实现 + 真机对服务器验证

### 9.5 仍然未解的风险（不因上面的进展而消失）

- 若尾部 37 字节确实是对记录的 **MAC/签名**，则即使算法与布局全部还原，
  **仍需要密钥才能生成合法记录** —— 密钥可能是运行时派生、可能来自服务器。
- 服务端可能还有额外校验（版本、时间窗口）。

**结论：技术上已经"进了门"（混淆方案破解、工具链就位、噪音与逻辑可分离），
但"能不能真正上传"仍取决于密钥是否可从静态代码中取得。**

## 11. 间接表 dump 结果 ⇒ 这是**控制流平坦化 / VM 式分发**

用 `docs/rev/table.py`（遍历表内每个 8 字节槽，拿已知不透明常量族去解）dump
`0x18c2fe0`–`0x18c32c8`（93 个槽），发现槽值有决定性规律：

```
0x18c2fe0  0x6b14cc6877520839
0x18c2fe8  0x6b14cc6877520a2d
0x18c2ff0  0x6b14cc6877521aa5
0x18c3000  0x6b14cc6877520c4d
...（93 个槽的高 48 位完全一致：0x6b14cc687752）
```

⇒ 整张表是**用同一个常量混淆过的指针表**，而且**差值被保留**：
`值ᵢ − 值ⱼ = 真实ᵢ − 真实ⱼ`。把低位排开：

```
0471 04bd 05c9 06d5 07ed 0865 09bd 09d5 0a2d 0a2d 0a61 0b69 0bc9 0c05 0c29
0c4d 0c71 0d8d 0da5 0f29 0f71 0f9d 0fc9 13dd 140d 14a1 15b1 15dd 1649
1a9d 1a9d 1aa5 1aa5 1aa5 1aad 1aad 1aad 1b01 1b49 1c1d
```

**跨度约 6 KB、93 个入口、间隔全是 4 的倍数** ⇒ 典型特征：
**93 个小 stub（每个约 8–16 条指令）挤在一段 6KB 代码里，由这张表间接分发** ——
也就是 OLLVM 的**控制流平坦化（或自研 VM 分发）**。

### 11.1 这对工作量的影响（重要）

之前以为"混淆只是几处隐藏调用"，现在看是**函数逻辑被拆成 ~93 个 handler 并表驱动分发**。
要静态还原算法，需要：
1. 先解出混淆密钥（用"差值保留"这个性质 + 定位那 6KB 的 handler 区）
2. 再逐个读 93 个 handler，重建分发的状态机（这已接近"逆向一个自研 VM"）

工作量从"读 477 行"变成"**逆向一个 VM + 93 个 handler**"，而且 `encode_record`
（1588 行）里同样有 46 处走这张表 ⇒ 两个函数都受影响。

### 11.2 这条路的现实评估

- **仍然可行但成本大幅上升**；静态路线的下一小步是明确的：
  解出表的混淆密钥 → dump 那 6KB handler 区 → 看 handler 的形态（是否真有 VM 字节流）。
- **更务实的替代**：动态分析（root 的安卓设备/模拟器上跑 Frida，或 Windows 版用调试器）
  直接 hook `encode_record`/`custom_enc` 的入参出参，跳过静态还原 ——
  但需要一个能跑起来并被调试的环境（Windows 版最容易，因为本机就能跑）。
- 无论哪条路，**"尾部 37 字节是不是 MAC、密钥从哪来"这个根本问题依然悬着**。

### 11.3 给决策用的一句话

现状：混淆比预期重（VM 式），静态还原是"能走但很贵"的路；
动态分析（本机 Windows 版 + 调试器 hook）可能几小时内就能拿到"输入→输出"的映射，
但**只能得到行为，不一定能得到可复现的算法**（若密钥随机/来自服务器则仍然没戏）。
